# Архитектура приложения Список постов

Исходники и скомпилированные изображения Sequence, C4 (уровни C1–C3) и ERD доступны в разделе [архитектурных диаграмм](diagrams/README.md).

Приложение — статическое SPA на React 19 и TypeScript. Оно читает посты из JSONPlaceholder напрямую из браузера. Собственный backend и база данных не добавлены: в задании нет серверной бизнес-логики, авторизации или операций постоянного хранения.

## Контекст и границы

В системе участвуют три компонента:

1. браузер выполняет React-приложение и хранит состояние навигации;
2. JSONPlaceholder отвечает на запросы списка и отдельного поста;
3. Nginx раздаёт production-сборку и поддерживает fallback для клиентских маршрутов.

API считается внешней недоверенной системой. Клиент обрабатывает сетевые ошибки и проверяет структуру ответа через Zod. Nginx не проксирует API и не хранит данные.

## Маршруты

| URL | Назначение | Состояние в URL |
| --- | --- | --- |
| `/` | Перенаправление к списку | — |
| `/posts` | Список постов | `page`, `limit` |
| `/posts/:postId` | Детали поста | `postId` в параметре пути |

Канонический адрес списка имеет вид `/posts?page=1&limit=10`. Query-параметры делают выбранную страницу воспроизводимой после обновления браузера и при передаче ссылки. Неизвестные или недопустимые значения нормализуются до поддерживаемых значений до запроса API.

## Структура модулей

```text
src/
├── app/                       # точка сборки приложения, router, providers
├── entities/
│   └── post/                  # типы, схемы, API и представление поста
├── features/
│   └── posts-pagination/      # limit, page и элементы пагинации
├── pages/                     # композиция маршрутов списка и деталей
├── shared/                    # конфигурация, HTTP-утилиты, общий UI
└── test/                      # setup тестов и общие обработчики MSW
```

Зависимости направлены от верхнего уровня к нижнему:

- `app` может подключать страницы и глобальные провайдеры;
- `pages` компонуют сущности, функции и общие элементы;
- `features` реализуют законченное пользовательское действие и используют публичный интерфейс сущности;
- `entities` описывают предметную сущность и её API-контракт;
- `shared` не зависит от бизнес-модулей.

Такое разделение не является отдельным фреймворком. Для небольшого задания оно задаёт явные места для маршрутизации, данных, пагинации и общих утилит, не создавая backend-слоёв, которые сейчас не нужны.

## Поток данных списка

1. Страница списка читает `page` и `limit` из URL.
2. Нормализованные значения входят в ключ запроса TanStack Query.
3. API-функция отправляет `GET /posts?_page=<page>&_limit=<limit>` на базовый адрес из `VITE_API_BASE_URL`.
4. Zod проверяет массив постов перед возвратом в UI.
5. TanStack Query предоставляет странице состояния загрузки, успешного ответа и ошибки.
6. Пагинация изменяет query-параметры; новый ключ запроса переключает данные на выбранную страницу.

Серверное состояние не дублируется в глобальном клиентском store. TanStack Query отвечает за данные API, React Router — за состояние URL, а локальное состояние компонента используется только там, где оно не должно переживать навигацию.

## Поток данных деталей

1. React Router извлекает `postId` из `/posts/:postId`.
2. После проверки идентификатора API-функция запрашивает `GET /posts/<postId>`.
3. Схема Zod проверяет объект поста.
4. Страница отображает данные либо явное состояние загрузки, отсутствия ресурса или ошибки.

Идентификатор включается в ключ TanStack Query, поэтому кеши разных постов не пересекаются.

## Контракт внешнего API

Минимальная модель поста содержит числовые `userId` и `id`, а также строковые `title` и `body`. Все значения поступают извне и считаются неизвестными до успешной проверки схемой.

Базовый адрес читается из `VITE_API_BASE_URL`. Значение публично и встраивается Vite во время сборки; секреты в нём хранить нельзя. API должен разрешать браузерные CORS-запросы и быть доступен по HTTPS при публичном развёртывании.

## Пагинация

Текущая страница начинается с `1`. Поддерживаемые лимиты задаются интерфейсом, а при смене лимита страница сбрасывается на первую, чтобы не оставить пользователя за пределами доступного диапазона. Запрос списка передаёт оба параметра вместе.

Пагинация не предполагает бесконечного набора данных. Возможность следующего перехода определяется данными ответа API; UI не должен обещать страницу, наличие которой не подтверждено.

## Обработка ошибок

На уровне интерфейса различаются:

- начальная загрузка;
- пустой список;
- сетевая или HTTP-ошибка;
- ответ, не соответствующий схеме;
- отсутствие отдельного поста;
- неизвестный клиентский маршрут.

Пользователь получает понятное сообщение и доступное действие восстановления там, где повторный запрос имеет смысл. Технические подробности не выводятся как необработанная трассировка.

## Сборка и контейнер

Dockerfile использует два этапа:

1. Node.js 22 Alpine устанавливает зависимости и выполняет production-сборку Vite;
2. Nginx Alpine получает только статические файлы и конфигурацию сервера.

Контейнер слушает HTTP внутри Docker, а Compose публикует приложение на `localhost:8080` и выполняет healthcheck. Правило SPA fallback возвращает `index.html` для клиентского маршрута, если статического файла с таким именем нет. Поэтому прямое открытие `/posts/:postId` не превращается в ответ Nginx `404`.

## Принятые решения

| Решение | Почему | Следствие |
| --- | --- | --- |
| Статическое SPA без backend | Все требуемые данные доступны из открытого API | Меньше инфраструктуры, но доступность зависит от внешнего сервиса |
| URL как источник состояния списка | Страницу и лимит можно сохранить и передать | Параметры нужно нормализовать централизованно |
| TanStack Query вместо самописного кеша | Нужны стандартные состояния запросов и разделение кеша | Ключи запросов должны включать параметры данных |
| Zod на границе API | TypeScript не проверяет данные во время выполнения | Ошибка схемы обрабатывается как контролируемая ошибка данных |
| Nginx для production | Сборка Vite состоит из статических файлов | Требуется SPA fallback для React Router |

## Не входит в архитектуру

Авторизация, CRUD, SSR, собственная база, серверная пагинация вне возможностей выбранного API и мониторинг production-среды не входят в объём тестового задания. Если источник данных или требования изменятся, эти решения следует пересмотреть, а не встраивать заранее.
