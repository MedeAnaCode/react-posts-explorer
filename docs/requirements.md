## Критерии приёмки

### Список постов

1. При открытии `/` пользователь попадает на страницу списка `/posts`.
2. URL `/posts?page=1&limit=10` показывает первую страницу и использует лимит 10.
3. Переход на другую страницу обновляет `page` в URL и отправляет запрос с `page` и `page-size`.
4. Смена лимита обновляет `limit`, возвращает пользователя на первую страницу и инициирует новый запрос.
5. Во время запроса виден статус загрузки; при пустом ответе и ошибке показаны отдельные понятные состояния.
6. Каждый отображённый пост можно открыть с помощью ссылки или клавиатуры.

### Детали поста

1. URL `/posts/:postId` сохраняет и запрашивает строковый Guardian ID, включая разделяющие его слеши.
2. Заголовок, раздел, дата и текст успешного ответа отображаются на странице деталей; автор и иллюстрация показываются при наличии.
3. Загрузка, ошибка сети, некорректные данные и отсутствие поста не приводят к пустому экрану или необработанному исключению.
4. Прямое открытие маршрута работает и в dev-сервере, и в Nginx-контейнере.

### Качество и поставка

1. `npm run check`, `npm run build` и `npm run test:e2e` завершаются с кодом `0` в подготовленном окружении.
2. `docker compose up --build -d` публикует приложение на `http://localhost:8080`, а контейнер переходит в состояние `healthy`.
3. В клиентскую сборку не включены секреты; `GUARDIAN_API_KEY` используется только dev/preview proxy и runtime-конфигурацией Nginx.
4. Код разделён по назначению: сборка приложения, сущность поста, пагинация, страницы, общая инфраструктура и тестовые утилиты не смешаны в одном модуле.
5. Репозиторий содержит исходное задание, инструкции запуска, архитектурные решения и историю осмысленных коммитов.

## Границы приёмки

Задание не требует собственного прикладного backend, базы данных, авторизации, создания или редактирования постов. Узкий proxy для защиты API key входит в инфраструктуру доставки, но не хранит и не преобразует новости. SLA, лимиты и состав данных Guardian Content API находятся вне контроля приложения.
