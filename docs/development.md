# Разработка и проверка

Этот документ описывает воспроизводимую локальную разработку, уровни тестирования и условия готовности изменения. Команды выполняются из корня репозитория.

## Требования к окружению

- Node.js 22.13 или новее;
- npm из поставки Node.js;
- Git;
- Docker с Compose для проверки production-контейнера;
- Chromium для end-to-end тестов Playwright.

Проверить версии:

```bash
node --version
npm --version
git --version
docker version
docker compose version
```

## Первичная настройка

```bash
npm ci
cp .env.example .env
npx playwright install chromium
```

PowerShell-вариант копирования окружения:

```powershell
Copy-Item .env.example .env
```

Локальный `.env` не коммитится. В нём нужен выданный Guardian API key:

```dotenv
GUARDIAN_API_KEY=replace-with-your-guardian-api-key
```

Vite читает значение на серверной стороне и добавляет его только к проксируемым запросам `/guardian-api`. Не добавляйте префикс `VITE_`: такие переменные доступны клиентскому коду и могут попасть в сборку.

## Ежедневная разработка

```bash
npm run dev
```

Рабочий цикл для изменения:

1. создать тематическую ветку от актуальной интеграционной ветки;
2. внести небольшое законченное изменение;
3. обновить тесты и документацию вместе с поведением;
4. выполнить быстрые проверки во время работы;
5. перед объединением выполнить полный локальный набор проверок;
6. просмотреть diff и исключить секреты, артефакты сборки и случайные файлы.

## Модель веток и коммитов

- `master` содержит проверенный результат, готовый к публикации;
- `develop` объединяет завершённые функции перед релизом;
- `feature/*` изолирует отдельную функцию или техническое изменение;
- `release/*` используется только для финальной стабилизации, если она нужна.

Сообщения коммитов следуют Conventional Commits и описывают результат по-русски:

```text
feat: добавить выбор лимита постов
fix: нормализовать номер страницы из url
test: проверить ошибку загрузки поста
docs: уточнить запуск контейнера
```

Коммит должен быть осмысленной проверяемой единицей. Форматирование всего проекта не смешивается с функциональным изменением без необходимости.

## Команды качества

| Команда | Когда запускать | Результат |
| --- | --- | --- |
| `npm run format:check` | перед коммитом | форматирование соответствует конфигурации |
| `npm run lint` | перед коммитом | ESLint не сообщает ошибок |
| `npm run typecheck` | после изменения типов и API | TypeScript проверен без генерации файлов |
| `npm run test` | после изменения поведения | модульные и интеграционные тесты проходят |
| `npm run test:coverage` | перед итоговой сдачей | сформирован локальный отчёт о покрытии |
| `npm run build` | перед объединением ветки | production-сборка создаётся успешно |
| `npm run test:e2e` | перед итоговой сдачей | пользовательские сценарии проходят в браузере |
| `npm run check` | перед объединением ветки | объединённые проверки проекта проходят |

`npm run format` изменяет файлы. После него нужно повторно просмотреть diff и запустить `npm run format:check`.

## Автоматические проверки в GitHub

Workflow `.github/workflows/ci.yml` работает в трёх режимах:

1. `push` в любую ветку запускает `Lint (non-blocking)`. Ошибки ESLint видны в логе и GitHub Summary, но не делают workflow красным.
2. `pull_request` в `master` запускает блокирующие `Unit tests`, `End-to-end tests` и `Production readiness`.
3. `workflow_dispatch` вручную запускает тот же полный набор перед production-релизом.

Итоговый job `PR gate` зависит от всех блокирующих проверок. В настройках защиты `master` его нужно выбрать как обязательный status check; после этого GitHub не позволит объединить pull request с упавшими unit-, end-to-end или production-проверками.

`Production readiness` проверяет форматирование, TypeScript и runtime-зависимости, собирает реальный Docker-образ и запускает его для smoke-теста `/healthz`, прямого SPA-маршрута и HTTP security headers. Это выявляет проблемы именно в поставляемом образе, а не только в dev-сервере.

## Стратегия тестирования

### Модульные тесты

Vitest проверяет чистую логику: разбор и нормализацию параметров, схемы данных и правила пагинации. Эти тесты не должны обращаться к реальной сети.

### Интеграционные тесты компонентов

Testing Library проверяет поведение, доступное пользователю, а MSW перехватывает HTTP-запросы. Основные сценарии:

- успешная загрузка списка;
- загрузка, пустой ответ и ошибка;
- изменение страницы и лимита;
- открытие и отображение отдельного поста;
- ошибка или отсутствие отдельного поста;
- несоответствие ответа ожидаемой схеме.

Тесты ищут элементы по доступной роли, имени и видимому тексту, а не по внутренней структуре компонентов.

### End-to-end тесты

Playwright запускает собранное пользовательское приложение и проверяет сквозные сценарии:

- открытие списка;
- переход по пагинации;
- смена лимита;
- переход к деталям поста;
- прямое открытие маршрута деталей.

Запуск:

```bash
npm run test:e2e
```

Если браузер ещё не установлен:

```bash
npx playwright install chromium
```

## Ручная проверка

После автоматических тестов проверьте:

1. `/posts?page=1&limit=10` открывается напрямую;
2. кнопки пагинации доступны с клавиатуры и имеют понятные имена;
3. смена лимита возвращает список на первую страницу;
4. URL меняется вместе с состоянием списка;
5. переход к новости и прямое открытие URL со строковым Guardian ID работают;
6. загрузка и ошибка не вызывают скачков разметки или пустого экрана;
7. интерфейс остаётся читаемым на узком и широком экране.

## Проверка Docker-сборки

```bash
docker compose up --build -d
docker compose ps
```

Ожидаемый результат: сервис доступен на `http://localhost:8080`, а после периода запуска контейнер имеет статус `healthy`.

Проверьте корневой маршрут, список и прямой маршрут деталей. Затем остановите окружение:

```bash
docker compose down
```

`GUARDIAN_API_KEY` является runtime-переменной Nginx-контейнера и обязательна для Compose. При смене ключа достаточно пересоздать контейнер; в образ и клиентские файлы значение не встраивается.

## Диагностика

**`npm ci` сообщает о несовместимой версии Node.js.** Переключитесь на Node.js 22.13 или новее и повторите установку с lock-файлом.

**Playwright не находит браузер.** Выполните `npx playwright install chromium` от того же пользователя и повторите `npm run test:e2e`.

**Guardian API отвечает 401 или 403.** Проверьте наличие и корректность `GUARDIAN_API_KEY`, затем перезапустите Vite или пересоздайте контейнер.

**Маршрут `/guardian-api` возвращает ошибку proxy.** Проверьте доступ к `https://content.guardianapis.com` с машины или контейнера. Браузер не должен обращаться к Guardian напрямую.

**Прямой маршрут возвращает Nginx 404.** Убедитесь, что контейнер использует конфигурацию из репозитория со SPA fallback, затем пересоберите образ.

**Docker продолжает отдавать старую версию.** Выполните повторную сборку через `docker compose up --build -d` и проверьте, какой образ запущен.

## Готовность изменения

Изменение готово к объединению, когда:

- выполнены относящиеся к нему критерии из [requirements.md](requirements.md);
- добавлены или обновлены тесты наблюдаемого поведения;
- комментарии объясняют только неочевидные решения и ограничения;
- `npm run check` и `npm run build` проходят;
- для пользовательского сценария проходит `npm run test:e2e`;
- production-контейнер собирается и становится здоровым;
- документация соответствует фактическим командам и структуре;
- в diff и production-сборке нет секретов, временных файлов и результатов сборки.
